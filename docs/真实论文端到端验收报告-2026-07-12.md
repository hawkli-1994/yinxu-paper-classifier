本轮使用 `essay/` 中 5 篇真实论文，共 67 个 PDF 页面，按真实桌面流程逐篇执行：

1. 新建论文项目；
2. PDF.js + MuPDF 本地文本准备；

4. 结构化结果与逐字证据校验；

本轮修复包括：

- 为 PDF.js 配置中文 CMap、标准字体、WASM 和系统字体；
- 增加 MuPDF 本地文本引擎，并修复 PDF.js 转移输入缓冲区后导致 MuPDF 回退失效的问题；
- 扩展证据标准化，兼容全半角、PDF 控制字符、空格和中英文标点差异；
- 拦截云端 OCR 返回中的 `<|LOC...|>`、`<|REF...|>` 和替换字符等模型伪影；
- 强制 Agent 在写入主分类及字段证据前回查 `text.jsonl`，只复制同一 PDF 页中的连续原文；
- 对“逐字引文正确但页码偏移”的情况做唯一匹配页确定性校正；
- 字段证据异常现在会降低置信度，不再出现“有校验问题仍是 100 分”；
- 限定 `ruleConflicts` 只记录个人规则或知识包规则冲突，版面混排和 OCR 问题不再误扣 25 分。

## 4. OCR 三态策略

设置页现在提供单选的三种执行模式：

- **自动**：先用本地双引擎判断页面是否可读；需 OCR 时优先云端。云端失败或返回低质量文本时，保留本地结果并标记人工复核。没有 OCR Key 时仍能走本地路径。
- **本地**：只使用 PDF.js + MuPDF，绝不调用云端，也不要求 OCR Key。纯图片扫描件可能无法识别，会明确标记需复核。
- **云端**：每一页都必须调用云端 OCR；没有 OCR Key 时阻止保存或导入；任一云端调用失败时终止导入，不静默回退本地。

需要特别说明：当前“本地”路径是本地 PDF 文本解析，不是完整的离线视觉 OCR。若未来要求无网络识别纯扫描件，应再内置 PaddleOCR/ONNX Runtime 等本地视觉模型。

## 5. 作为用户的产品评价

### 已达到可用水平的部分

- 主分类在本组真实论文上稳定且符合论文核心研究问题；
- 作者、题名和主分类证据总体可直接用于复核；
- 逐字证据和 PDF 页码已有程序校验，不再只相信模型自述；
- 自动模式不会为了“使用 OCR”而上传本地已能读取的论文；
- 失败和低质量结果会保留审计信息，适合学术 Demo 的单人工作流。

### 仍需继续改进的部分

1. **样本量仍小**：5 篇只能证明当前材料类型可行，不能代表 72 个三级类都达到同等准确率。下一阶段应为每个易混类别建立带专家答案的金标准集。
2. **互见分类存在运行波动**：同一篇论文复跑时，主类稳定，但 C32、C41 等互见类有时保留、有时省略。互见分类应增加更明确的独立论证门槛，或在复核界面突出为可选建议。
3. **分类体系的史实正确性仍需专家确认**：本轮只能确认 Agent 忠实执行现有知识包，不能替代博士生对类别定义、年代和术语的专业审校。
4. **本地纯扫描识别能力尚未建立**：MuPDF 能解决异常字体和文本层问题，但不能替代视觉 OCR。
5. **运行时间偏长且有随机性**：单篇 Agent 分类约 76—194 秒；更严格的证据回查会增加耗时。后续可把元数据、证据定位做成确定性预处理，减少 Agent 工具调用。
6. **中断恢复需继续加固**：测试期间曾出现窗口关闭后项目停留在 `processing` 的情况；正式版本应在重启时把无活动锁的运行标记为“已中断，可重试”。

## 6. 结论与建议

当前智能体不需要更换主模型或重写分类工作流。真实数据表明，最有效的改进方向是继续把“模型容易犯错的机械环节”下沉为确定性程序：文本解析、OCR 质量门控、证据逐字匹配、页码纠正、分类代码校验和置信度计算。

建议下一阶段优先级：

1. 建立 20—50 篇专家标注的易混类别回归集；
2. 收紧互见分类的稳定性规则；
3. 增加中断运行恢复；
4. 视真实扫描件比例决定是否内置离线视觉 OCR；
5. 博士生反馈到达后，以知识包版本升级方式修正分类定义，并让旧项目保留原知识包版本用于审计。
